Note非規範の実装計画

このリポジトリはプロトコル仕様と検査実装を管理しており、対局サービス本体、アカウントDB、認証APIは含まない。本計画は別のsecurity/authorization profileと、そのprofileを利用するホストの実装手順を示す。認証機能の実装完了を表す文書ではない。

目的と現在の契約

アクセス資格を検証し、ゲーム・記録・座席・viewの許可を確認してから情報を配信する。規範本文§18と仕様策定プロセス§6に従い、認証方式は別profileで定義する。

現在確定していること実装への制約
信頼境界を越える通信には機密性と相手認証が必要TLS等をtransport adapterで適用する
session/game/request IDは資格情報ではないIDの所持だけで権限を与えない
joinのmode/view/seat/targetには閉じた文法がある標準のauth memberやerror codeを独自追加しない
resumeはplayだけ、一回使用、期限付き、成功時rotate外部の資格検証後も§13の状態遷移を維持する
publicは情報投影の種類匿名アクセスを許すかは対象ごとの認可policyで定める
snapshotと再送も同じview制約に従う認可後にそのsessionの投影と不変ledgerだけを配信する

実装構成

flowchart LR
  A[接続と資格情報] --> B[transport adapterで資格検証]
  B --> C[principalを接続に束縛]
  C --> D[YAMAI hello / joinの検査]
  D --> E[game / target / seat / viewを認可]
  E --> F[座席予約またはresumeを原子的に確定]
  F --> G[welcomeと許可viewの配送]

資格情報の検証器、対象ごとの認可判定器、session/token保管を独立した責務にする。ホスト内部の認可入力はprincipal、対象ID、mode/view、希望座席、操作、policyの版とする。これらは内部APIの値であり、YAMAI wire memberを追加する提案ではない。

許可規則は明示的に定義し、該当する許可がなければ拒否する。認証済みでも対象ごとの許可は別に検査する。この設計の参考はOWASP Authorization Cheat Sheetである。

対象ごとの認可

操作検査する権限・条件許可時の状態
新規playroomへの参加資格、希望座席の利用資格と空席seat省略時はcoreが規定する最小空席を割り当てる
spectatetarget gameの観戦公開設定public viewを新sessionへ投影する
replay publicgameまたはrecordingの閲覧資格join時点の記録prefixを固定する
replay seat/full対象とviewの個別許可、進行中対局の秘匿policy許可された投影だけを送る
resume外部資格、既存sessionに結び付いた権限、token・期限元のseat/viewを保持し、旧接続と旧tokenを同時に無効化する
ログ参照運用者の対象別権限tokenや未公開牌を診断へ出さない

認可後のseat変更や暗黙のview縮小は行わず、許可できない要求は拒否する。利用資格の失効時は外部profileに定めた方法で配送と再開資格を停止し、ゲームの時計・既に確定した選択は巻き戻さない。

段階と成果物

Steps0/5

1. security/authorization profileを文書化する。 対象ホスト、principalの識別方法、資格情報の発行元、期限・失効、匿名観戦の条件、公開前の牌譜、拒否時の応答を定める。profileの版と固定された正負fixtureを用意する。方式と配備先は現リポジトリから決定できないため、ホスト実装の着手前に確定する。

P1

2. transport adapterへ資格検証を実装する。 最初の対応transportを選び、そのハンドシェイクや保護された外部経路で資格情報を受け取る。HTTPを使う場合のstatus、Cookieを使う場合のOrigin/CSRF対策、TLS終端との信頼関係をprofileで固定する。資格情報はURL・対局message・診断ログへ出さない。

P1

3. ホストの交渉処理へ認可を接続する。 構造・版・profile等のcore検査と、profileが規定する認可処理の順序を決める。権限検査と座席予約の間の競合を防ぎ、失敗時にseat、seq、tokenを消費しない。標準error codeの意味を認可拒否へ流用しない。必要な追加応答は別profileのtransport契約または正式な拡張で定義する。

P1

4. resume保管と失効処理を接続する。 tokenは128 bit以上の暗号学的乱数から生成し、検証用hash等で保管する。同じtokenの同時再開を直列化し、welcomeのキュー記録成功を境に一回だけrotateする。期限ちょうど、権限失効、保存状態喪失、welcome配送失敗、旧接続からの入力を別々に検査する。

P1

5. 正負fixtureと独立ホストで検証する。 現在のcoreの検査に加え、許可表の全組合せ、他人のtarget/seat指定、権限の途中失効、resume競合、ログ・snapshotへの秘匿漏れを検査する。採用したホスト実装の起動から配信までを確認し、結果とprofileの版を記録する。

P1

受け入れ条件

AUTH-01資格を要求する対象では、資格なし・失効済み・改変済みの要求で対局情報を取得できず、座席予約も発生しない。匿名閲覧を許す対象でも、明示されたpublic viewの範囲を超えられない。Todo
AUTH-02同一principalでも許可されていないgame・recording・seat・viewへ移れない。Todo
AUTH-03同じresume tokenの同時使用は最大1件だけ成功し、失敗した検査ではtokenを消費しない。Todo
AUTH-04resume後の旧接続は入力を変更できず、失効でrequestの時計を延長しない。Todo
AUTH-05ログ、エラー、snapshot、再送にtokenや許可外の手牌を含めない。Todo
AUTH-06coreのSchema・状態検査を維持し、auth profileのfixtureとホスト実装の統合試験を通過する。Todo

提供範囲と着手条件

認証基盤の選択、実際のホストリポジトリ、公開・匿名閲覧の運用policyは本計画の実装入力である。今回の仕様レビューではそれらを導入せず、coreとの責務境界と検証可能な受け入れ条件を定めた。core単体のテスト成功を、認証サービスの稼働や公開サービスの適合性として表明しない。
